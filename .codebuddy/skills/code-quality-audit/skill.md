# Code Quality Audit

> 审查方法论 + 严重度标准 + 修复决策树 + 报告模板。
> 不包含具体文件/热点——那些由 Agent 运行时通过读代码动态发现。

## 审查前置：项目文档参考

审查代码质量前，建议按需读取以下文档，避免将"有意设计"误判为问题：

| 文档 | 读取场景 |
|------|---------|
| `docs/context/EDGE_CASES.md` | 审查 D1/D2 时——已知陷阱和特殊处理已记录在此 |

## 审查维度（9 维度）

### D1: 安全性与健壮性 — "代码会崩溃吗？"

重点关注：`!` force unwrap、`try!`、`as!`、`try?` 静默错误、数组越界、指针操作安全性。

**严重度**：
- P0: force unwrap/as! 可被外部输入触发
- P1: force unwrap 理论安全但缺防御
- P2: `try?` 静默错误但不影响核心功能

**发现技巧**：`rg '!' --type swift` 快速定位，结合上下文判断是否有 guard 保护。

---

### D2: 并发安全 — "有数据竞争吗？"

重点关注：`@unchecked Sendable` 的 mutable state 保护、`@Observable` 线程安全、actor 内阻塞操作、回调 `@Sendable` 标注、NSLock vs actor 选择。

**严重度**：
- P0: `@unchecked Sendable` + mutable state 无保护
- P0: 非 `@MainActor` 代码访问 `UIApplication.shared`
- P1: 回调未标 `@Sendable`
- P2: 不必要的 `@MainActor` 或过度 actor 隔离

**发现技巧**：`rg '@unchecked Sendable'`、`rg 'UIApplication.shared'` 定位候选，逐个检查保护机制。

---

### D3: 架构合规（五层架构）— "依赖方向正确吗？"

重点关注：Foundation 层 import 外部框架、Engine 层绕过 Infrastructure 层直接调用基础设施 API、Presentation 层执行业务逻辑/I/O。

**严重度**：
- P1: Foundation 层依赖外部框架
- P1: Engine 层绕过 Infrastructure 层
- P2: 类型定义位置不理想

**发现技巧**：`rg '^import' Foundation/` 检查 Foundation 层导入，只有 `Foundation`/`OSLog` 是允许的。

---

### D4: 依赖注入合规 — "有硬编码依赖吗？"

重点关注：`.shared` 单例残留、构造器是否接受协议、`UserDefaults.standard` 直接访问、全局状态访问。

**严重度**：
- P1: 非 deprecated 的 `.shared` 单例
- P2: deprecated 的 `.shared` 仍在被调用

**发现技巧**：`rg '\.shared'` 全局搜索，区分已 deprecated 和未 deprecated。

---

### D5: 职责单一性 — "做太多事了吗？"

重点关注：函数 >50 行、文件 >400 行、一文件多公共类型、参数 >5 个、嵌套 >3 层。

**严重度**：
- P1: 函数 >100 行
- P2: 函数 50-100 行、文件 >400 行但结构清晰

**发现技巧**：`tokei` 统计行数，重点审查最长的文件/函数。

---

### D6: 重复与冗余 — "DRY 违反了吗？"

重点关注：复制粘贴代码段、冗余 import、死代码、相似功能不同实现、重复初始化模式。

**严重度**：
- P1: 核心算法重复实现（可能导致行为不一致）
- P2: 工具方法重复、冗余 import

**发现技巧**：`codebase_search` 搜索相似函数名/算法名，比较实现差异。

---

### D7: 命名与可读性 — "读得懂吗？"

重点关注：模糊变量名、文件名与内容不匹配、注释与代码不一致、方法名不反映副作用、魔法数字、命名风格不一致。

**严重度**：
- P1: 方法名有误导性
- P2: 魔法数字、命名风格不一致

---

### D8: 设计系统一致性（仅 Presentation 层）— "UI 遵循规范了吗？"

重点关注：硬编码间距/圆角/颜色（未使用 Asset Catalog 或设计常量）、Combine 替代 Swift Concurrency、View 中执行 I/O。

**严重度**：
- P1: View 中执行文件/网络操作
- P2: 未使用设计常量、使用 Combine 替代 async/await

**发现技巧**：在 Presentation/ 下搜索数字字面量（间距/圆角候选），与 Asset Catalog 对比。

---

### D9: 代码坏味道 — "凭直觉，对劲吗？"

D1-D8 的补充，捕捉规则性检查遗漏的"工程直觉"问题。**不与 D1-D8 重复**。

四类坏味道：
- **结构**：过度封装、空壳抽象、中间人、数据泥团、特性依恋
- **逻辑**：过度防御、不自然控制流、布尔盲区、原始类型偏执
- **生命周期**：僵尸代码、幽灵依赖、遗留适配器
- **语义**：名不副实、层级错位、过度泛化、误导性注释

**严重度**：
- P1: 过度封装/空壳抽象显著增加导航成本（3+ 层跳转）、名不副实导致误解、僵尸代码 >20 行
- P2: 不自然控制流、原始类型偏执、过度防御

**审查原则**：区分"坏味道"和"风格偏好"——只有增加认知负担或维护成本的才算发现。

## 审查原则

**要做**：具体行号 + 代码片段 + 修复代码 + 影响范围评估
**不做**：不报告通用最佳实践、不报告 `#if DEBUG` 内容、不将 actor async 标记为问题、不建议引入外部依赖、标准算法常数不要求提取

## 修复决策树

> 供 fixer 使用。不要机械替换，按决策树判断。

### D1 Force Unwrap

```
发现 force unwrap (!)
  ├─ 上下文有 guard/if let 保护同一变量？ → 安全，标记为误报
  ├─ 是 precondition 场景（不可恢复）？ → 保留，加注释说明
  ├─ 输入来自外部（用户/系统/框架）？ → P0，必须 guard let
  └─ 输入来自内部计算（理论不会为 nil）？ → guard let + Logger.warning

guard let 的 else 分支语义：
  ├─ 在循环内且该项可跳过？ → continue
  ├─ 函数可以提前返回空结果？ → return []
  ├─ 有合理的 fallback 值？ → 使用 fallback
  └─ 无法容忍缺失？ → throw 或 assertionFailure + return
  ⚠️ 绝对不能静默丢弃数据而不记录日志
```

### D2 @unchecked Sendable

```
发现 @unchecked Sendable
  ├─ 所有 mutable state 被 NSLock/锁保护？
  │   ├─ 有同步调用路径（性能关键）？ → 保留锁，加安全注释
  │   └─ 全是 async 调用？ → 转 actor
  ├─ 用 @Observable？
  │   ├─ 只在 MainActor 上使用？ → 加 @MainActor
  │   └─ 跨 actor 使用？ → 需要拆分状态，报告给主 Agent
  └─ 无保护？ → P0，必须修复（actor 或加锁）
```

### D3 Foundation 层 import

```
发现 Foundation 层 import 外部框架
  ├─ 只用了一个类型？ → 定义纯 Swift 替代类型
  ├─ 用了框架 API？ → 提取到协议，Infrastructure 层实现
  └─ 是条件编译 #if canImport？ → 移到适配层
```

### D4 .shared 单例

```
发现 .shared 使用
  ├─ 已标记 deprecated？
  │   ├─ 调用方能通过 DI 获取？ → 替换为注入
  │   └─ 调用方还没有注入路径？ → 标记 TODO，本轮跳过
  ├─ 未标记 deprecated？ → 先标记 deprecated + 添加 init 注入路径
  └─ 在实例方法内用 .shared 代替 self？ → 直接替换为 self
```

### D6 重复代码

```
发现重复实现
  ├─ 两个实现行为一致？ → 提取到共享位置，两处都改为调用
  ├─ 两个实现有细微差异？
  │   ├─ 差异是 bug？ → 修复 bug + 提取
  │   └─ 差异是有意的？ → 保留两个，加注释说明
  └─ 不确定？ → 报告给主 Agent，不自行合并
```

### D9 代码坏味道

```
发现 D9 坏味道
  ├─ 结构坏味道
  │   ├─ 过度封装/中间人 → 内联到调用方，删除空壳类型
  │   ├─ 空壳抽象（唯一实现且非 DI/测试需要）→ 删除协议
  │   └─ 形式化参数对象 → 评估是否多处使用
  │
  ├─ 逻辑坏味道
  │   ├─ 过度防御 → 删除冗余 guard，注释说明
  │   ├─ 不自然控制流 → 重写为函数式（仅当可读性确实提升）
  │   └─ 布尔盲区 → 拆分方法或引入 enum
  │
  ├─ 生命周期坏味道
  │   ├─ 僵尸代码 → 直接删除
  │   ├─ 幽灵依赖 → 直接删除
  │   └─ 遗留适配器 → 确认旧 API 不存在后删除
  │
  └─ 语义坏味道
      ├─ 名不副实 → 重命名（必须搜索全部引用）
      ├─ 层级错位 → 报告给主 Agent 确认
      └─ 过度泛化 → 特化为具体类型

⚠️ 不确定是"坏味道"还是"有意设计" → 报告给主 Agent，不自行修复
```
